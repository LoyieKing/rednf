## 服务端引用但上游与线上都没有的表（rednf 反推补齐）

`remake-extra.sql.in` 里补了 53 张表，每张表上方都注明了推出它的源码位置。来源有两处：
一是 remake 源码里的 SQL 字符串，二是 ORIG ELF（`.origin_1031` 的 `df_game_r`、`df_dbmw_r` 等）的 `strings`。
两边交叉核对后，只收录真正被当作表名使用的名字；只出现在报错文本里的名字（`IDMap`、`HumanCertifyCount` 等）没有收录。

推导规则：

- **库**：`GetDBHandle(N)` / dbmw 的 `m_handles[N]` 里的 N 就是 `db_connect.db_type`（见 `GlobalData/QueryConnInfo.inc`），
  dbmw 的 `m_handles[0]` 用于 d_technical_report。
- **列与类型**：取自 INSERT、UPDATE、SELECT 用到的列和格式符（`%d` 对应 int，`%u` 对应 unsigned，`%hhd` 对应 tinyint，`'%s'` 对应 varchar）；
  能找到读取代码的，按 `get_str(len)`、`get_float`、`get_binary` 定长度和类型。
- **主键**：按 upsert 语句的 WHERE 条件推出主键或唯一键；纯日志表只建普通索引。
- **字符集与引擎**：字符集一律 utf8；引擎跟随同库的多数表（`_log`、`_secu`、`_se_event`、technical_report 用 MyISAM，其余用 InnoDB）。
- **仅查询目录**：表名只出现在 `CQueryCounter` 的 ORIG 查询目录里（这是一张用于统计的字符串表），remake 与 ORIG 的现有代码路径都不会执行这些语句；
  这类表的所在库都是猜测。

“猜测项”这一列：`库` 表示所在库是按命名和邻表推断的；`occ_check` 这一列只出现在 `where occ_check!=0` 条件里，
类型按 int 处理；其余列出的项是 varchar 长度或类型无法从绑定代码确定、按惯例取的值。SQL 里对应的列也标了 `-- 猜测`。

另外两点：

- `school_member` 在 `_UpdateSchoolCharac` 里用的是句柄 16，而 `db_connect` 里没有 db_type 16，所以这条路径本来就取不到句柄（原版行为）。
- 按年月分表的表（`log_response_time_YYYYMM`、`churn_reward_history_YYYYMM`、`member_mousepass_history_YYYYMM`、
  `auction_history_YYYYMM` 等）上游只带了部分月份。服务端按当前月份拼表名，遇到缺失的月份会报错，需要时按同前缀的已有表 `LIKE` 建表。
